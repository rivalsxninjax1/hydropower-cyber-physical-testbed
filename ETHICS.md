# Ethics and Safety Statement

## Purpose

This repository is a final-year academic cybersecurity project: a
self-contained, fully simulated cyber-physical testbed for studying
how cyberattacks against industrial control systems (ICS) propagate
into physical consequences, how they can be detected, and how network
architecture affects whether they succeed at all. Its purpose is
educational and research-oriented — to produce evidence and
understanding, not to provide a ready-made attack toolkit.

## This project targets nothing real

Every component in this repository — the physical process, the PLC,
the HMI, the network, and the "victim" being attacked — is simulated
software running inside Docker containers on the developer's own
machine. Specifically:

- **No real hydropower plant, dam, or industrial facility is
  represented, connected to, or in any way involved.** The physics
  model (`simulation/physics_engine/`) is an illustrative simplified
  model built for this project, explicitly documented as such in
  `docs/architecture/physics-model.md`, with every simplifying
  assumption stated rather than hidden.
- **No real PLC, RTU, or vendor hardware is used or emulated in a way
  that resembles a specific commercial product.** The PLC
  (`industrial/plc/`) is original code implementing the standard,
  public Modbus TCP protocol against a register map defined entirely
  within this project.
- **All network communication is confined to Docker's internal
  networking** (`docker-compose.yml`, `docker-compose.segmented.yml`).
  The attacker container has no code, credentials, or configuration
  that references any IP address, hostname, or network outside this
  project's own Docker Compose networks. This was verified by direct
  inspection during development, not merely assumed — every attacker
  script (`attacker/tools/`) takes its target host as an explicit
  command-line argument pointing at the project's own `plc` container,
  never a hardcoded external address.
- **No component in this project makes outbound connections to the
  public internet** as part of its normal operation (the frontend
  pages load web fonts from Google Fonts via the *browser*, which is
  unrelated to the simulated ICS network itself).

## Why an intentionally vulnerable system was built

The PLC's Modbus interface has no authentication (documented explicitly
in `docs/architecture/plc-register-map.md`). This is not an oversight
— it is the deliberate, stated baseline condition the project's
experiments are designed to study, matching a real and well-documented
characteristic of legacy Modbus TCP deployments in actual industrial
environments. The project's later phases (network segmentation,
intrusion detection) exist specifically to measure how much that
vulnerability can be mitigated without changing the protocol itself,
since in practice many real ICS devices cannot be easily patched or
upgraded to add authentication.

## No CTF elements

Per the project's own design brief, this is explicitly **not** built
as a capture-the-flag exercise: there are no flags, no scoring, no
leaderboards, and no gamified "challenges." Every experiment
(`experiments/`) is framed as a research question with a stated
hypothesis, method, and measured result — see
`experiments/01-modbus-control/README.md` and
`experiments/02-network-segmentation/README.md` for examples.

## Responsible use

The attacker tools in `attacker/tools/` (`network_scan.py`,
`modbus_recon.py`, `modbus_probe_writable.py`, `exploit_gate.py`) and
the experiment scripts in `experiments/` are functional network and
Modbus TCP tools. Used against this project's own containers, they
demonstrate the attack techniques documented in
`docs/threat-model/threat-model.md`. **These same tools would function
identically against a real Modbus TCP device if pointed at one.**

If you use, adapt, or extend this project:

- Only ever run these tools against systems you own or have explicit,
  documented authorization to test.
- Unauthorized access to computer systems, including industrial
  control systems, is illegal in most jurisdictions regardless of
  intent.
- If you are studying this project to understand ICS security, treat
  the documented vulnerabilities and techniques as material for
  defensive learning, not as an invitation to test them against
  systems outside this repository's own isolated environment.

## Data handling

No real personal data, credentials, or proprietary information of any
kind is used anywhere in this project. All data generated by running
the testbed (`data/logs/`, `data/experiments/`, `data/pcaps/`) is
synthetic — produced entirely by this project's own simulated
components — and contains nothing sensitive.

## Questions or concerns

This project was built as an academic capstone. If you have questions
about its scope, safety design, or intended use, refer first to
`docs/architecture/` (technical design rationale) and
`docs/threat-model/threat-model.md` (what is and is not covered), both
of which document design decisions and their reasoning in detail.
